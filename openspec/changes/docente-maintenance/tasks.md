## Merge gate (read first: "main" auto-deploys to production)

Pushing to "main" deploys to production. Only the tracker "feat/docente-maintenance" ever merges to "main", and only when ALL of the following hold. Slice PRs merge into the tracker, which does not deploy. Never delete the tracker or the slice branches after merge.

1. Slices 1 to 4 (and "-5-integration-suite" if the stop line created it) are merged into the tracker in order with merge commits; "npm test", "npm run typecheck", "npx eslint src" (CRLF rule) and "npm run build" are green on the tracker tip; "sdd-verify" passes (tasks 6.0, 6.1).
2. The Postgres integration suite and the system test RF-12 are green on a fresh disposable Neon branch with the current 17 migrations, with the commit hash and the evidence table recorded (Phase 5, task 5.10).
3. The read-only production count below is 0, repeated on the day of the merge; the informative duplicate-email count is recorded (task 6.3). If it is not 0 the tracker does NOT merge: the owner receives the grupo ids (no personal data) and reassigns or deactivates each grupo through the existing screens, then the count is repeated. No direct SQL write.
4. The owner gives an explicit yes for the merge to "main" and the single production deploy (task 6.4). Merging to "main", every Neon command and every deletion always need an explicit yes, whatever approval was recorded in task 0.2 for slice PRs. There is no migration, dependency or environment variable, so nothing is written to production by this change except what the owner does in the smoke test.
5. The rollback is known to the owner (task 6.6).

```sql
-- must return 0 (read-only, production)
select count(*) from "Grupo" g join "Usuario" u on u."Id" = g."DocenteId"

-- informative only (read-only, production): lower-case emails held by more than one account
```

Writes happen only on a disposable Neon branch. NEVER use "validacion-secretaria" or "validacion-estudiantes" for writes, and never write to production.

## Conventions

> Notation: T(<filters>) is the command "$env:DATABASE_URL='postgres://u:p@127.0.0.1:9/x'; npm test -- <filters>"; each filter is a substring of a test path and unit runs never touch a database. Branch names, commands, SQL, placeholders and string values are written in double quotes; only real repository file paths are backticked (a path the task edits or creates). A path a task only reads carries (read-only).
> Strict TDD (vitest): a behavior-changing task is a RED task (write the failing test, run it, confirm the failure) followed by its GREEN task. A test that passes at write time (it pins existing behavior) says so and carries a revert-only mutation check. Vitest does not typecheck, so "npm run typecheck" is its own gate. Postgres cases (the whole of unit 12, slice 4) are skipped by "npm test" and by "npm run test:integration" without the INTEGRATION env, so their RED/GREEN proof is the run of Phase 5 plus the PG-only mutation checks of task 5.3.
> Gates per unit (G): the focused T(...) run, "npm run typecheck", "npx eslint <touched files> | rg -v 'Delete .␍.'" (CRLF rule of `openspec/config.yaml`), "npx prettier --check <touched files> --end-of-line auto"; when `i18n/es.json` or `i18n/en.json` change, also T(src/i18n). Gates per slice (GS): full "npm test" (dummy DB as in T), "npm run typecheck", "npx eslint src | rg -v 'Delete .␍.'", "npm run build" (dummy DATABASE_URL set), then the size measurement.
> Mutation checks (MC): a temporary edit of the production file that must make the named test fail, undone with "git restore <file>"; "git status" is confirmed clean of it before every commit. Every check, with the failing test name, is recorded in `openspec/changes/docente-maintenance/apply-progress.md`.
> Size measurement: "git diff --numstat <slice base> HEAD -- . ':(exclude)openspec' ':(exclude)docs'" summed over added plus deleted lines; "package-lock.json" and ".engram/" are never counted nor staged. Stop line: 1000 per PR, checked at each slice close (tasks 1.12, 2.11, 3.11, 4.15). There are no intermediate checkpoints.
> DB rule (`CLAUDE.md`): apply never runs "drizzle-kit migrate", "drizzle-kit push", "db:seed", "neon" write commands or SQL writes on its own. Every database task is tagged [ASK OWNER]; a write is also tagged [CONFIRM] and needs the owner's explicit "yes" for that exact command, never batched. Read-only queries are tagged [READ-ONLY]. Merging to "main", every Neon command and every deletion always need an explicit yes. No env file is read or committed: the owner sets the variables in the shell session. No mail leaves the process: the suite uses only the fakes of `src/lib/intake/fakes.ts` (read-only), never `getIntakeDeps`.
> Spec IDs: DM-1..DM-18 (`specs/docente-maintenance`), DM-AUD-1..DM-AUD-3 (`specs/audit-log`), SAC-AUD-1 plus the modified SR-16 and FE-27 (`specs/staff-account-creation`), CM-ACC-1 and CM-LST-1 (`specs/catalog-management`), AC-MW (`specs/academic-catalog`, "Manual writes require an active Asignatura and an active docente"), CEI-VAL, CEI-UPS, CEI-UI (`specs/catalog-excel-import`: "Per-row validation with row-level errors", "Natural-key upserts", "Import UI flow and copy"), IAP-KEEP (`specs/imported-account-provisioning`, "Existing accounts keep their credentials"). A1..A12 are the design decisions of `openspec/changes/docente-maintenance/design.md`; D1..D5 the owner decisions of the proposal. SC-1..SC-13 are the Postgres cases of tasks 4.9 to 4.14; ST-1..ST-13 are the steps of the system test sheet in Phase 5.
> Threat matrix (design: application boundaries only): direct POST by another role (2.1, 2.6, 2.7); foreign id of another role (1.7, 1.8, 2.6); mass assignment of "login", "rol", "activo" (1.4, 1.8, 2.6); actor forging (2.6, 4.1); mutation by GET (2.8, 3.7). Shell, subprocess, VCS, executable-file and process boundaries: N/A.
> Language: code, comments, copy keys and artifacts are English except the es values of the catalogs and `docs/` (Spanish, as the files are). Catalog copy follows the register of the neighbouring `catalog.asignaturas` lines; no new colour, radius, type size or spacing step (`docs/design-system.md` is not edited unless task 4.7 finds something new).
> Never stage (named as text, not as edit targets): the file "FORMATO SOLICTUD DE JUSTIFICACION DE AUSENCIA.docx", the folders "constancias_ficticias/" and "infra/modal/__pycache__/", the file "package-lock.json", and anything under ".engram/". The owner's staged edit of "docs/flow-experience-backlog.md" and the backlog itself are not touched by this change.
> Skills for apply: work-unit-commits, chained-pr. One commit per work unit (tests and code together), Conventional Commits, no AI attribution, no "Co-Authored-By".
> Edit authority: a backticked path on a checkbox line is an edit target; read-only references carry (read-only).
> Size note: the sdd-tasks cap (530 words) is exceeded on purpose; the repository precedent keeps one line per task with spec links and a Verify line.
> Chain: tracker "feat/docente-maintenance" (from main c5ea22e); four planned slice branches, stacked, each cut from the previous one: "feat/docente-maintenance-1-domain", "-2-actions", "-3-ui", "-4-closing"; "-5-integration-suite" exists only if slice 4 measures over 1000 at its close. Each slice PR opens against the tracker only after the previous slice is merged into it, and merges into the tracker in order with a merge commit ("gh pr merge --merge", never squash or rebase). If GitHub shows earlier slices in a diff, merge the tracker into the slice branch (merge commit) until the diff is clean. Branches are never deleted. Only the tracker merges to main.
> Approval of slice PRs: one task per slice opens the PR to the tracker and merges it under the approval recorded in task 0.2 (per-PR approval by the owner unless the owner gave a standing approval for slice PRs to the tracker with all gates green).

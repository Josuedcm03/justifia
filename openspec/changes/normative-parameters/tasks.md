## Merge gate (read first: "main" auto-deploys to production)

Pushing to "main" deploys to production. Only the tracker "feat/normative-parameters" ever merges to "main", and only when ALL of the following hold, in this order. Slice PRs merge into the tracker, which does not deploy. Never delete the tracker or a slice branch after merge.

1. All 13 slices (Phases 1 to 13) are merged into the tracker, in order, with merge commits (task 15.0).
2. Gates are green on the tracker tip: "DATABASE_URL=postgres://u:p@localhost:5432/x npm test"; "npx next typegen" then "npm run typecheck"; eslint with the rule `{"prettier/prettier":["error",{"endOfLine":"auto"}]}` over "src"; "npm run build" with a dummy DATABASE_URL and AUTH_SECRET (task 15.1).
3. The Postgres integration suite is green on a disposable Neon branch. Applying 0017 and 0018 to that branch is a schema command: each needs the owner's explicit yes for that exact command (tasks 14.1 to 14.6).
4. "sdd-verify" returns PASS on the tracker tip (task 15.1).
5. The owner system test passes in a preview deployment: each family (the six scalars, the calendar, the causes, the type-to-cause map) is changed in the running preview and its effect is seen on the next request, with no redeploy (NP-14; tasks 14.7 to 14.10).
6. Migration 0017 and then migration 0018 are applied to production, each with the owner's explicit yes for that exact command, BEFORE the tracker merges to "main"; then a read-only check shows the nine seed rows (tasks 15.3 to 15.5). Both migrations are additive or widening, so the code in production keeps working while they wait. Merging before 0017 keeps every read on defaults but makes every save fail.
7. The owner gives an explicit yes to open the PR "feat/normative-parameters" into "main" and to merge it (task 15.6). Merging to "main", every Neon command and every deletion always need an explicit yes, whatever approval was recorded in task 0.2 for slice PRs.

Writes happen only on a disposable Neon branch. NEVER use "validacion-secretaria" or "validacion-estudiantes" for writes, and never write to production except the two migrations of gate item 6.

## Conventions

> Notation: T(<filters>) is the command "DATABASE_URL=postgres://u:p@localhost:5432/x npm test -- <filters>" (PowerShell: "$env:DATABASE_URL='postgres://u:p@localhost:5432/x'; npm test -- <filters>"); each filter is a substring of a test path and unit runs never reach a database. Branch names, commands, SQL, placeholders and string values are in double quotes; only real repository file paths are backticked (a path the task edits, creates or deletes). A path a task only reads carries (read-only).
> Strict TDD (vitest): a behavior-changing task is a RED task (write the failing test, run it, confirm it fails for the right reason), then its GREEN task, then a REFACTOR task (clean up with the tests green, run the gates and mutation checks, commit). A test that passes at write time (it pins existing behavior) says so and carries a revert-only mutation check. Vitest does not typecheck, so "npx next typegen" plus "npm run typecheck" is its own gate. Postgres cases ([PG]) are skipped by "npm test" and by "npm run test:integration" without the INTEGRATION env, so their RED/GREEN proof is the run of Phase 14 plus its PG-only mutation checks.
> Gates per unit (G): the focused T(...) run, "npx next typegen" then "npm run typecheck", "npx eslint <touched files> --rule '{\"prettier/prettier\":[\"error\",{\"endOfLine\":\"auto\"}]}'", "npx prettier --check <touched files> --end-of-line auto"; when `i18n/es.json` or `i18n/en.json` change, also T(src/i18n). Gates per slice (GS): full "npm test" (dummy DATABASE_URL as in T), "npx next typegen" then "npm run typecheck", "npx eslint src" with the same rule, "npm run build" with dummy DATABASE_URL and AUTH_SECRET, then the size measurement.
> Mutation checks (MC): a temporary edit of the production file that must make the named test fail, undone with "git restore <file>"; "git status" is confirmed clean of it before every commit. Every check, with the failing test name, is recorded in `openspec/changes/normative-parameters/apply-progress.md`.
> Size measurement: "git diff --numstat <slice base> HEAD -- . ':(exclude)openspec' ':(exclude)docs' ':(exclude)drizzle/meta'" summed over added plus deleted lines (the generated snapshot JSON is excluded from the authored budget); "package-lock.json" and ".engram/" are never counted nor staged. Stop line: 1000 per PR, checked at each slice close. There are no intermediate checkpoints.
> DB rule (`CLAUDE.md`): apply never runs "drizzle-kit migrate", "drizzle-kit push", "db:seed", "neon" write commands or SQL writes on its own. Every database task is tagged [ASK OWNER]; a write is also tagged [CONFIRM] and needs the owner's explicit "yes" for that exact command, never batched. Read-only queries are tagged [READ-ONLY]. "npm run db:generate" reads `src/db/schema.ts` only and never connects to a database, so it needs no confirmation. No env file is read or committed: the owner sets the variables in the shell session. The suite never calls a real mail sender or a real store: only the fakes of `src/lib/intake/fakes.ts` (read-only).
> Spec IDs: NP-1..NP-17 (`specs/normative-parameters`); NP-AUD-1..NP-AUD-3 (`specs/audit-log`); BS-NAV-1 (`specs/backoffice-shell`); consumer deltas by requirement name: RR-QUEUE ("Queue ordering and RN-08 alert", `specs/request-review`), VS-RN07 ("Late presentation, RN-07"), VS-RN14 ("Recurrence, RN-14"), VS-MD15 ("MD-15 ... one parameter table behind an injectable seam") (`specs/validation-signals`), JI-CAUSE ("Cause and dates rules"), JI-SUBMIT ("Submit blocking, per field") (`specs/justification-intake`), SD-UPLOAD ("Upload authorization and limits"), SD-FINALIZE ("Finalize with magic-byte validation"), SD-LIMIT ("Maximum size reaches every upload path, the client and the database") (`specs/supporting-documents`). A1..A18 are the design decisions of `openspec/changes/normative-parameters/design.md`; D1..D8 the owner decisions of the proposal. ST-1..ST-14 are the steps of the system test sheet in Phase 14; PG-1..PG-6 are the Postgres case groups 1 to 6 of the design's Testing Strategy.
> Threat matrix (design: application boundaries only): direct POST or GET by a non-secretaria identity (9.1, 9.3, 10.4, ST-2); write without the confirmation marker (9.3, 10.1); mass assignment of a key outside the registry or the action's closed set (8.3, 9.3, 11.1); out-of-range, non-integer or malformed values, validated in the action and again in the write (1.1, 8.3, 9.3); causes list that is not a permutation or has no active cause (1.1, 13.1); actor forging (9.3, 8.5); audit leak, closed payloads and calendar dates only (8.1, 11.1); unbounded input, calendar at most 1000 entries (1.1, 11.1). Shell, subprocess, VCS/PR automation, executable-file and process boundaries: N/A.
> Language: code, comments, copy keys and artifacts are English except the es values of the catalogs and `docs/` (Spanish, as the files are). es copy is neutral professional Spanish with no voseo. No new colour, radius, type size or spacing step (`docs/design-system.md` is edited only if a task finds something new).
> Next.js rule (`AGENTS.md`): before the first Next code of a slice read the relevant guide in `node_modules/next/dist/docs/` (read-only), and record the rule applied in `apply-progress.md`. Slices 9 and 10 (server actions, `revalidatePath`, `redirect`, caching) need it explicitly.

> Chain: tracker "feat/normative-parameters" (cut from main after the planning documents). Each slice PR opens against the tracker only after the previous slice is merged into it, and merges in order with a merge commit ("gh pr merge --merge", never squash or rebase). If GitHub shows earlier slices in a diff, merge the tracker into the slice branch (merge commit) until the diff is clean. Branches are never deleted. Only the tracker merges to "main".
> Approval of slice PRs: one task per slice opens the PR to the tracker and merges it under the approval recorded in task 0.2. The approval never covers the merge to "main", a Neon command or a deletion.

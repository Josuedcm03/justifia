## Conventions

> Notation: T(<filters>) is the command "DATABASE_URL=postgres://u:p@localhost:5432/x npm test -- <filters>" (PowerShell: "$env:DATABASE_URL='postgres://u:p@localhost:5432/x'; npm test -- <filters>"); each filter is a substring of a test path and unit runs never reach a database. Branch names, commands, SQL, placeholders and string values are in double quotes; only real repository file paths are backticked (a path the task edits, creates or deletes). A path a task only reads carries (read-only).
> Scope cuts (owner, 2026-11-27): the eight cuts are listed in `proposal.md` ("Scope cuts") and in `apply-progress.md` ("Scope cuts (owner, 2026-11-27)"). They turn the 13-slice plan into 10 numbered slices, remove migration 0018 and the 25 MiB ceiling, remove mutation checks from slice 5 on, shrink the system test to 7 steps and trim the page. Slices 1 to 4 are merged: their checked tasks stay as written (their PR bodies say "of 13"); a "Scope cut note" under a phase says what changed for it. Removed tasks keep their number as a "Removed" line so that references stay valid; Phases 11 to 13 no longer exist (numbers left unused so that Phases 14 to 16 keep theirs).
> Strict TDD (vitest): a behavior-changing task is a RED task (write the failing test, run it, confirm it fails for the right reason), then its GREEN task, then a REFACTOR task (clean up with the tests green, run the gates, commit). A test that passes at write time (it pins existing behavior) says so. Vitest does not typecheck, so "npx next typegen" plus "npm run typecheck" is its own gate. Postgres cases ([PG]) are skipped by "npm test" and by "npm run test:integration" without the INTEGRATION env, so their proof is the run of task 14.5.
> Gates per unit (G): the focused T(...) run, "npx next typegen" then "npm run typecheck", "npx eslint <touched files> --rule '{\"prettier/prettier\":[\"error\",{\"endOfLine\":\"auto\"}]}'", "npx prettier --check <touched files> --end-of-line auto"; when `i18n/es.json` or `i18n/en.json` change, also T(src/i18n). Gates per slice (GS): full "npm test" (dummy DATABASE_URL as in T), "npx next typegen" then "npm run typecheck", "npx eslint src" with the same rule, "npm run build" with dummy DATABASE_URL and AUTH_SECRET, then the size measurement.
> Mutation checks (MC): run in slices 1 to 4 only (a temporary edit of the production file that must make the named test fail; records in `openspec/changes/normative-parameters/apply-progress.md`). There are none from slice 5 on (owner scope cut, 2026-11-27). Before every commit "git status" is confirmed to hold only the unit's files.
> Size measurement: "git diff --numstat <slice base> HEAD -- . ':(exclude)openspec' ':(exclude)docs' ':(exclude)drizzle/meta'" summed over added plus deleted lines (the generated snapshot JSON is excluded from the authored budget); "package-lock.json" and ".engram/" are never counted nor staged. Stop line: 1000 per PR, checked at each slice close; slices 9 and 10 carry a pre-approved size exception up to 1500 (owner pre-approved up to 1500 on 2026-11-27), and over 1500 follows the stop line. There are no intermediate checkpoints.
> DB rule (`CLAUDE.md`): apply never runs "drizzle-kit migrate", "drizzle-kit push", "db:seed", "neon" write commands or SQL writes on its own. Every database task is tagged [ASK OWNER]; a write is also tagged [CONFIRM] and needs the owner's explicit "yes" for that exact command, never batched. Read-only queries are tagged [READ-ONLY]. "npm run db:generate" reads `src/db/schema.ts` only and never connects to a database, so it needs no confirmation. No env file is read or committed: the owner sets the variables in the shell session. The suite never calls a real mail sender or a real store: only the fakes of `src/lib/intake/fakes.ts` (read-only).
> Spec IDs: NP-1..NP-17 (`specs/normative-parameters`); NP-AUD-1..NP-AUD-3 (`specs/audit-log`); BS-NAV-1 (`specs/backoffice-shell`); consumer deltas by requirement name: RR-QUEUE ("Queue ordering and RN-08 alert", `specs/request-review`), VS-RN07 ("Late presentation, RN-07"), VS-RN14 ("Recurrence, RN-14"), VS-MD15 ("MD-15 ... one parameter table behind an injectable seam") (`specs/validation-signals`), JI-CAUSE ("Cause and dates rules"), JI-SUBMIT ("Submit blocking, per field") (`specs/justification-intake`), SD-UPLOAD ("Upload authorization and limits"), SD-FINALIZE ("Finalize with magic-byte validation"), SD-LIMIT ("Maximum size reaches every upload path and the client, within the database check") (`specs/supporting-documents`). ST-1..ST-7 are the steps of the system test sheet in Phase 14; PG-1, PG-3, PG-4 and PG-5 are the Postgres case groups of the design's Testing Strategy (groups 2 and 6 were removed by the scope cuts).

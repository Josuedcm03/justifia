# Data Table Specification (new capability)

> Delta type: this whole file is ADDED. There is no base spec for `data-table`.

## Purpose

The shared contract of every data table in the backoffice: how list state lives
in the URL, how sorting, search, filtering, page size and paging behave, how a
table is operated by keyboard and assistive technology, and how it shows
empty, no-results, pending and degraded states. The contract has two usage
modes:

- **Server-driven**: the users, asignaturas and docentes lists. The URL is the
  state and the server is the source of truth (D2, D3).
- **Bounded**: the Grupos section of the Asignatura edit page, the import
  `CountsTable` and the import errors table. They have no URL state, no
  sorting, no paging and no toolbar, and gain no capability (A7).

What each list shows, its scope, its sortable columns and its search fields
stay with `users-listing` and `catalog-management`. The shell states are owned
by `backoffice-shell`.

Traceability (checked against `docs/requirements.md`):

- RNF-01 (a), "authorization is verified on the server": new URL parameters
  never widen the session-derived scope. Regression guard, not a new feature.
- RNF-01 is NOT cited for DT-DATA-1 (data exposure): its wording covers denying
  an unauthorized page or action without returning data, not what an authorized
  viewer's rows carry to the browser. DT-DATA-1 therefore cites no RNF.
- RNF-10 is motivation only and is not claimed (verified in the pilot).
- Accessibility cites `docs/design-system.md` section 7; i18n cites
  `openspec/config.yaml` conventions. Neither is an RNF.
- Out of scope by owner decision: live or debounced search (D5), a no-JS
  fallback (D6), colour changes (D1).

URL parameters, in canonical order: `q`, `status` (lists that have a filter),
`sort` (a column key), `dir` (`asc` or `desc`), `size` and `page`.

| Parameter | Accepted values | Default (omitted from generated URLs) |
|---|---|---|
| `q` | trimmed, whitespace collapsed, capped at 100 characters | empty |
| `status` | `active`, `inactive`, `all` | users `all`; catalog lists `active` |
| `sort` | users `name`, `login`, `role`, `status`, `created`; asignaturas `code`, `name`, `hours`, `status`; docentes `name`, `login`, `email`, `status` | users `created`; asignaturas `code`; docentes `name` |
| `dir` | `asc`, `desc` | users `desc`; catalog lists `asc` |
| `size` | `10`, `25`, `50` | `10` |
| `page` | ASCII digits, at least 1 | `1` |

## Requirements

### Requirement: DT-URL-1 URL state with safe fallbacks

On a server-driven list the state of the view MUST be held in the URL so that
reloading or sharing the URL shows the same view. Every parameter MUST be parsed
on the server against its closed set of accepted values by exact,
case-sensitive match. An unknown, malformed, differently-cased, empty, repeated
(array) or hostile value MUST fall back to that parameter's default and MUST
NOT cause an error page, a failed request or a different data scope. `sort` and
`dir` resolve together: a valid `sort` with a valid `dir` is used; a valid
`sort` with a missing or invalid `dir` is ascending; a missing or invalid
`sort` gives the list's default pair and `dir` is ignored. Links generated by
the table MUST omit every parameter equal to its default, MUST write `sort` and
`dir` together or not at all, and MUST write the parameters in the canonical
order above.

#### Scenario: Fallback table (table-driven)

| Parameter | Value in URL | Effective value |
|---|---|---|
| `sort` | absent, empty, `nope`, `NAME`, `name,id`, `hashClave`, `__proto__`, `name; DROP TABLE x`, 500 characters | the list's default sort and default direction |
| `sort` | repeated (`sort=name&sort=login`) | default sort and direction |
| `sort` | a column key of another list (`hours` on docentes) | default sort and direction |
| `dir` | `up`, `DESC`, `ASC`, empty, `1`, repeated, with a valid `sort` | `asc` |
| `dir` | any value, with a missing or invalid `sort` | ignored (default direction) |
| `status` | `bogus`, `ACTIVE`, empty, repeated | the list's default status |
| `size` | `0`, `-5`, `5`, `100`, `1000`, `10.5`, `010`, `abc`, empty, `1e1`, repeated | `10` |
| `page` | see the page rules of the list (DT-URL-3) | page 1 or nearest valid page |

- GIVEN a list with enough rows for several pages
- WHEN it is requested with the value from the row
- THEN the response renders normally with the effective value from the row
- AND no error page, no thrown error and no query error occurs

#### Scenario: Valid values are honoured

- GIVEN a list requested with `sort=<valid column>`, `dir=desc` and `size=25`
- WHEN it renders
- THEN rows are ordered by that column descending, 25 per page
- AND reloading the same URL shows the same view

#### Scenario: Sort never reaches the query as text

- GIVEN any value of `sort` from the fallback table
- WHEN the list query is built
- THEN the order comes only from a fixed server-side mapping of accepted column
  keys, and a value outside the mapping produces the default order

#### Scenario: Generated links omit defaults (table-driven)

| State | Generated query string |
|---|---|
| all defaults | none (the bare path) |
| `q=ana`, default sort, page 2 | `?q=ana&page=2` |
| `sort=name`, direction `asc`, `size=25` (users) | `?sort=name&dir=asc&size=25` |
| default sort key with the non-default direction | `?sort=<key>&dir=<direction>` |

- GIVEN the state from the row
- WHEN a table link or form target is generated
- THEN it equals the string in the row

#### Scenario: Parameters do not change the data scope (RNF-01 a)

- GIVEN a viewer whose scope is restricted by role or by Carrera
- WHEN the list is requested with any combination of `sort`, `dir`, `status`,
  `size`, `page` and `q`, valid or hostile, and with extra parameters such as
  `role=administrador` or `scope=all`
- THEN the rows, total and page count are always inside that viewer's scope
- AND the response is identical to the one without the extra parameters

### Requirement: DT-URL-2 Changing the view returns to page 1

Submitting a search, changing the status filter, changing the sort column or
direction, and changing the page size MUST each return the list to page 1. A
change of page alone MUST keep `q`, `status`, `sort`, `dir` and `size`. Every
other active parameter MUST survive a change of one parameter.

#### Scenario: Reset to page 1 (table-driven)

| Change made on page 3 |
|---|
| submit a search term |
| choose another status |
| activate a sortable header |
| reverse the sort direction |
| choose another page size |

- GIVEN a list on page 3 with a search term, a sort and a page size set
- WHEN the change from the row is made
- THEN the URL omits `page` (page 1) and the other parameters are kept
- AND page 1 of the new view is shown

#### Scenario: Paging keeps the view

- GIVEN a list with `q`, `status`, `sort`, `dir` and `size` set
- WHEN the user moves to next, previous, first or last page
- THEN only `page` changes in the URL

### Requirement: DT-URL-3 Page clamping against the real total

An out-of-range, non-numeric, zero, negative, fractional, empty or repeated
`page` MUST NOT error: below range and invalid values show page 1, and a value
above range shows the last page, computed on the server from the total of the
current view (search, filter and page size included). After a change that
alters the number of pages, the page shown MUST be valid for the new total.

#### Scenario: Page larger than the new page count

- GIVEN 25 matching rows, `size=25` and `page=3`
- WHEN the list is requested
- THEN page 1 is shown (one page exists)

#### Scenario: Page clamps for each size

- GIVEN 60 rows and `page=99`
- WHEN requested with `size` 10, 25 and 50
- THEN the last page is shown in each case (6, 3 and 2)

### Requirement: DT-NAV-1 History behaviour of list controls

Controls that change which rows are shown (first, previous, next and last page,
the status filter and the search submit) MUST add a history entry. Controls that
only re-arrange the same result set (the sort header and the page-size
selector) MUST replace the current history entry. First, previous, next, last
and the status filter MUST be real links, so that opening one in a new tab or
with a modifier key keeps working. Changing a list view MUST NOT scroll the page
to the top.

#### Scenario: Back after a content change

- GIVEN a user on page 1 who moves to page 2 and then goes back
- WHEN the browser returns
- THEN page 1 of the same view is shown

#### Scenario: Back after sort or page size

- GIVEN a user on `/users` who sorts by name and then changes the page size
- WHEN they go back once
- THEN they leave the list (the previous entry), not the previous sort or size

#### Scenario: Links open in a new tab

- GIVEN the next-page control
- WHEN it is inspected
- THEN it is an anchor with a real `href` equal to the next page's URL

### Requirement: DT-SORT-1 Single-column sorting with a stable tie-breaker

Sorting is single-column. Only the columns listed for each list in its own spec
are sortable; every other column, including action columns and the Asignaturas
"Groups" column, MUST NOT be sortable. Rows tied on the chosen column MUST be
ordered by the list's default ordering, and finally by the record `id`
(following the chosen direction), so that the order is deterministic and no row
is skipped or repeated across pages, whatever the chosen column and direction.
Activating an unsorted sortable header MUST sort by it ascending; activating
the active header MUST reverse its direction. Sorting MUST NOT change the
scope, the search results, the total or the page count.

Collation rules (decided in design): person names and logins MUST sort with
Spanish-aware collation, so an accented letter sorts with its base letter and
case does not decide the order; codes (asignatura code, role code) sort by the
database default. Rows with an empty email MUST come last in both directions.
`status` ascending MUST mean active first, descending inactive first. These
rules are the same on every page.

#### Scenario: Stable across pages with equal sort keys (table-driven)

| List | Sortable column keys exercised |
|---|---|
| users | every sortable column of `users-listing` |
| asignaturas | every sortable column of `catalog-management` |
| docentes | every sortable column of `catalog-management` |

- GIVEN more rows than one page where many rows share the same value in the
  column from the row
- WHEN all pages are read for `asc` and for `desc`
- THEN every row appears exactly once across the pages
- AND repeating the request returns the same rows in the same order

#### Scenario: Ties fall back to the default order, then id

- GIVEN users sorted by `status` where several share the same status
- WHEN the list is read
- THEN rows with the same status appear in the list's default order (newest
  first), and rows equal on that too are ordered by id

#### Scenario: Accented names sort alphabetically

- GIVEN in-scope people named "Zoe", "Álvaro", "angel" and "Beatriz"
- WHEN sorted by `name` ascending
- THEN the order is "Álvaro", "angel", "Beatriz", "Zoe" (not after "Zoe")
- AND descending gives the exact reverse

#### Scenario: Empty emails last in both directions

- GIVEN docentes with emails "b@x.org", "a@x.org" and two with no email
- WHEN sorted by `email` ascending and then descending
- THEN the two without email are last in both, and the others are in email order
  or its reverse

#### Scenario: Status order

- GIVEN active and inactive rows
- WHEN sorted by `status` ascending, then descending
- THEN active rows come first, then inactive first

#### Scenario: Header activation cycle

- GIVEN a list with no sort in the URL
- WHEN the user activates the "name" header, then the same header again
- THEN the URL holds `sort=name` with ascending, then `dir=desc`
- AND each change returns to page 1

#### Scenario: Non-sortable columns

- GIVEN the rendered header row
- WHEN the headers of the action column and the Groups column are inspected
- THEN they contain no sort control and expose no `aria-sort`

#### Scenario: Sort survives a reload

- GIVEN a list sorted by a column descending
- WHEN the URL is reloaded
- THEN the same order and the same header state are shown

### Requirement: DT-SORT-2 Sortable headers are accessible

A sortable column header MUST contain a native button inside the `th`, named by
the column label, and at least 44px tall. The `th` of the sorted column MUST
expose `aria-sort` as `ascending` or `descending`; no other column MUST expose
`aria-sort`. The direction MUST also be visible as an indicator that does not
rely on colour alone, and an unsorted sortable column MUST show a distinct
"sortable" indicator. The button MUST be operable with Enter and Space and show
a visible focus indicator. After activation, focus MUST stay on the same header
control. The table caption MUST tell assistive-technology users that headers
with a button sort the table. Sorting and row hover MUST NOT animate.

#### Scenario: aria-sort follows the state (table-driven)

| URL | `aria-sort` on the sorted `th` |
|---|---|
| `sort=name` | `ascending` |
| `sort=name&dir=desc` | `descending` |
| no `sort` (default sort) | per the default sort, on that column only |

- GIVEN a list requested with the URL from the row
- WHEN the header row renders
- THEN exactly the sorted column has the value from the row, and no other column
  has `aria-sort`

#### Scenario: Keyboard operation

- GIVEN a keyboard-only user focused on a sortable header button
- WHEN they press Enter, and separately Space
- THEN the sort changes as for a pointer activation
- AND focus remains on that header button after the update

#### Scenario: Direction is not colour alone

- GIVEN a sorted column and an unsorted sortable column
- WHEN the headers are inspected
- THEN each shows an indicator distinguishing sorted-ascending, sorted-descending
  and sortable, and the column name stays available to assistive technology

### Requirement: DT-TOOL-1 Toolbar: search, filter and result count

The toolbar MUST hold the search form, the status filter where the list defines
one, and the result count. Search MUST be applied only when the form is
submitted (Enter or the submit control); typing alone MUST NOT change the URL or
the results (D5). The search input MUST have a visible label. The existing
search semantics (case-insensitive partial match, trimmed, literal `%` and `_`,
hostile input without error, capped length) MUST NOT change. The result count
MUST be in a polite live region that does not move focus when it changes, and
it MUST be the only place the total appears (the footer does not repeat it,
DT-PAG-1). The status filter MUST mark the selected option for assistive
technology.

#### Scenario: Search is submit-only

- GIVEN a list and a user typing a term in the search input
- WHEN they type without submitting
- THEN the URL and the rows are unchanged
- AND pressing Enter submits the term and returns to page 1

#### Scenario: Filter and search combine

- GIVEN a status filter and a search term
- WHEN both are active
- THEN rows match both, and the count and page count reflect both

#### Scenario: Count is announced politely

- GIVEN a change of search, filter, sort, page size or page
- WHEN the new results load
- THEN the count region is `role="status"` with `aria-live="polite"` and focus
  is not moved by the update

### Requirement: DT-PAG-1 Footer: page status, page size, first/previous/next/last

The table footer MUST show the page status only (the current page of the total
pages, for example "Page 2 of 3"), without the total result count, which is
shown once, in the toolbar (DT-TOOL-1); a page-size selector offering exactly
10, 25 and 50 (default 10, the same on all server-driven lists); and first,
previous, next and last controls, which MAY be icon controls provided each has
an accessible name. At the first page first and previous, and at the last page
next and last, MUST be unavailable: not operable and exposed to assistive
technology as disabled. The current page MUST be marked as current for
assistive technology. The selector MUST have an accessible name. All controls
MUST be operable by keyboard, show visible focus and have a 44px-tall touch
target. The footer MUST be omitted when the total of the current view fits in
the smallest page size (10 rows or fewer), including when there are no results.

#### Scenario: Bounds (table-driven)

| Page shown (3 pages) | First | Previous | Next | Last |
|---|---|---|---|---|
| 1 | unavailable | unavailable | available | available |
| 2 | available | available | available | available |
| 3 | available | available | unavailable | unavailable |

- GIVEN 25 rows and page size 10
- WHEN the page from the row is shown
- THEN the controls are as in the row
- AND the footer shows the page status "Page <n> of 3" and does not show the
  total count
- AND the toolbar shows "25 results" once

#### Scenario: First and last navigation

- GIVEN 25 rows, page size 10, viewing page 2
- WHEN the user activates last, then first
- THEN page 3 (5 rows) and then page 1 are shown

#### Scenario: Page-size selector options

- GIVEN a server-driven list with 60 rows
- WHEN the selector is opened
- THEN it offers exactly 10, 25 and 50 with the current size selected
- AND choosing 25 sets `size=25`, returns to page 1 and shows 25 rows

#### Scenario: Footer omitted when everything fits

- GIVEN a view with 10 results or fewer, and separately zero results
- WHEN the list renders
- THEN no footer, page-size selector or paging control is shown

#### Scenario: One page of a larger size

- GIVEN 20 results and `size=25`
- WHEN the list renders
- THEN the footer is shown with all four paging controls unavailable and the page
  status "Page 1 of 1"

### Requirement: DT-PEND-1 Pending feedback on same-route changes

While a URL change of a server-driven list is in flight (search, filter, sort,
page size or page), the route-level loading skeleton (BS-LOAD-1) MUST replace
the page content, the table region included, until the new results arrive. The
previous rows are not kept visible and no dimmed or half-updated table is shown;
the empty or no-results state MUST NOT flash in the skeleton's place. The
skeleton MUST be announced to assistive technology as busy, with a localized
loading label, and MUST be static under reduced motion. Because the list
remounts when the new results arrive, keyboard focus on a sortable header MUST
return to the same header control (DT-SORT-2).
(Owner decision, 2026-10-18: the skeleton replaces the rows on a same-route
change; keeping the previous rows visible is not required.)

#### Scenario: Update in progress

- GIVEN a list and a pending navigation caused by a sort change
- WHEN the update has not yet completed
- THEN the page content, including the table region, is replaced by the loading
  skeleton with the shell still in place
- AND the skeleton is exposed as busy with its loading label and the previous
  rows are not shown

#### Scenario: Pending ends

- GIVEN the same pending update
- WHEN the new results arrive
- THEN the skeleton is replaced by the new list and the toolbar count shows the
  new count

#### Scenario: Reduced motion

- GIVEN `prefers-reduced-motion: reduce`
- WHEN the skeleton is shown for a pending update
- THEN the busy state and the loading label are still exposed and nothing moves

#### Scenario: Focus returns to the sort header after the remount

- GIVEN a keyboard user who activated a sortable header and the skeleton replaced
  the list
- WHEN the new list is shown
- THEN focus is on the same sortable header control

### Requirement: DT-STATE-1 Empty, no-results and degraded states

A server-driven list MUST distinguish three situations. (1) Empty, with no
search or non-default filter active: the shared empty state instead of a table.
(2) No results, with a search term or a non-default filter active: the shared
no-results state, which MUST include a link that clears the search and the
filters and returns to page 1. (3) Degraded, when the read fails: the shared
degraded alert (BS-STATE-2), shown instead of the toolbar count, the table and
the footer, whatever parameters the URL carries. A table MUST NOT be rendered
with zero rows, and a degraded read MUST NOT show an empty or no-results
message or a count as if the read had succeeded. The decision between table and
empty state belongs to the list as a whole, not to a caller-supplied slot.

#### Scenario: Three situations (table-driven)

| Situation | Shown |
|---|---|
| no rows, no search, default filter | empty state, no table |
| no rows, search term or non-default filter | no-results state with clear link |
| read fails | degraded alert only |

- GIVEN a list in the situation from the row
- WHEN it renders
- THEN what is shown is as in the row

#### Scenario: Degraded with sort and page size

- GIVEN a failed read and a URL with `sort=name&dir=desc&size=25&page=2`
- WHEN the list renders
- THEN the degraded alert is shown and the page does not crash
- AND no table rows, no count and no "no results" text are shown

#### Scenario: Clear link restores the list

- GIVEN a no-results state caused by a term and a status filter
- WHEN the user activates the clear link
- THEN the unfiltered list for the viewer's scope is shown from page 1

### Requirement: DT-MODE-1 Bounded tables gain no list capability

The Grupos section table, the import `CountsTable` and the import errors table
MUST render through the same table primitives, keep a caption or accessible name
and column headers, and MUST NOT expose sorting, paging, page-size selection, a
toolbar or URL parameters. Their content, columns and row order MUST be exactly
what they show before this change. The Grupos section MUST keep the row order and
the cap note specified by CM-ASG-7. `CountsTable` MUST keep showing the same
counts as a fixed matrix. The import errors table MUST keep its four columns
(sheet, row, reason, value), the workbook-wide "no row" marker, the reason text
rule (catalog text when known, otherwise the raw code) and the order in which
the errors were reported. With zero rows a bounded table renders nothing.

#### Scenario: Grupos section order and cap unchanged

- GIVEN an Asignatura with more than 100 groups
- WHEN its edit page is opened
- THEN the section lists the 100 newest by period, ordered period descending,
  group number ascending, id ascending, with the cap note
- AND no header is a sort control and no pagination is shown

#### Scenario: CountsTable is a fixed matrix

- GIVEN an import preview
- WHEN the counts table renders
- THEN it shows the same figures as before in the same layout, with column
  headers and an accessible name, and no sort or paging control

#### Scenario: Import errors table is unchanged

- GIVEN an import with errors on "Asignaturas" row 4, "Grupos" row 9 with
  reason `dias.invalid` value "Luns", and one workbook-wide error with row 0
- WHEN the errors panel renders
- THEN the table shows the four columns, the errors in the order reported, the
  workbook-wide error with a dash in the row column, and the reason text from
  the catalog
- AND no header is a sort control and no paging or toolbar is shown

### Requirement: DT-DATA-1 Rows delivered to a client table carry only displayed fields

The rows handed to an interactive table MUST be plain serializable values that
contain exactly the fields the table displays, plus the row id. They MUST NOT
contain the password hash or any personal or account field that the table does
not display (for example identity numbers, phone numbers or e-mail addresses
that are not a column of that table). This MUST hold at two points: the list read
used by the page MUST NOT select such fields, and the props passed to the client
table MUST be picked field by field rather than passed through. No `Date` object
or function needs to cross the boundary: dates MUST arrive as text already
formatted for the viewer. This requirement cites no RNF (see Traceability).

#### Scenario: Users rows (table-driven by forbidden field)

| Forbidden in the delivered rows |
|---|
| password hash (`hashClave`) |
| identity number (`cif`) |
| phone (`telefono`) |
| e-mail (`correo`) |

- GIVEN the users list rendered for an `administrador`
- WHEN the props handed to the client table are serialized
- THEN none of the fields in the row appears, and each row has exactly its
  displayed fields (name, login, role, status, created label) plus the id

#### Scenario: Docentes rows carry no credential

- GIVEN the Docentes list rendered and its delivered data serialized
- WHEN searched for `HashClave`, a password, a temporary password or `Cif`
- THEN none is present, and each row has only the displayed fields and the id

#### Scenario: Asignaturas and Grupos rows

- GIVEN the Asignaturas list and the Grupos section rendered
- WHEN their delivered rows are inspected
- THEN each row has only the displayed fields and the id

### Requirement: DT-DENS-1 Density and press feedback unchanged

Table cell padding and the header row height MUST stay as documented in
`docs/design-system.md` (24px horizontal, 16px vertical cell padding, 48px header
row); a sortable header button MUST fit that height without enlarging rows or
changing the alignment of the label with the cell text. Buttons and controls
MUST NOT scale on press (Q7 decided: no press feedback by scale).

#### Scenario: Header height

- GIVEN a table with sortable and non-sortable headers
- WHEN the header row renders
- THEN its height is the documented 48px for both kinds

### Requirement: DT-A11Y-1 Table accessibility floor

Every table MUST have an accessible name and column headers associated with
their cells. Status values MUST be text, not colour alone. The pagination and
the search region MUST be landmarks with accessible labels. Contrast, visible
focus, 44px targets and meaning-not-by-colour follow `docs/design-system.md`
section 7.

#### Scenario: Structure

- GIVEN any rendered table
- WHEN its structure is inspected
- THEN it has an accessible name, `th` headers with scope for their columns, and
  status cells carry a text label

### Requirement: DT-I18N-1 Table copy in both locales

All table text (sort labels and caption sentence, indicator text, page-size
label and options, first/last labels, page status, updating text, empty and
no-results text, captions) MUST come from the i18n catalogs and exist in `es`
and `en`; counts and pages MUST be interpolated, not concatenated
(`openspec/config.yaml`).

#### Scenario: Key parity

- GIVEN the `es` and `en` catalogs
- WHEN the keys added by this change are compared
- THEN both define the same keys with non-empty values

#### Scenario: Copy per locale

- GIVEN the `es` locale, and separately `en`
- WHEN a list renders with results, no results and degraded
- THEN every visible table string is in that language

## Open points

- Resolved (design gate V1): the route-level skeleton does show again on a
  query-only navigation (observed by the owner). DT-PEND-1 describes that
  behaviour and the owner accepted it on 2026-10-18; the focus rule of
  DT-SORT-2 holds through the remount. Restoring focus for the other list
  controls (status filter, paging, search) is not required.
- Dependency (design gate S1): the Spanish-aware ordering of DT-SORT-1 depends
  on the database offering that collation. If it does not, the fallback is
  case-insensitive ordering under the database default, and accent-aware
  ordering would not hold; see Risks of the change.
